# π₀.₅ (Pi05) Policy

π₀.₅ is a **Vision-Language-Action model with open-world generalization**, from Physical Intelligence. The LeRobot implementation is adapted from their open source [OpenPI](https://github.com/Physical-Intelligence/openpi) repository.

## Model Overview

π₀.₅ represents a significant evolution from π₀, developed by [Physical Intelligence](https://www.physicalintelligence.company/blog/pi05) to address a big challenge in robotics: **open-world generalization**. While robots can perform impressive tasks in controlled environments, π₀.₅ is designed to generalize to entirely new environments and situations that were never seen during training.

### The Generalization Challenge

As Physical Intelligence explains, the fundamental challenge isn't performing tasks of agility or dexterity, but generalization, the ability to correctly perform tasks in new settings with new objects. Consider a robot cleaning different homes: each home has different objects in different places. Generalization must occur at multiple levels:

- **Physical Level**: Understanding how to pick up a spoon (by the handle) or plate (by the edge), even with unseen objects in cluttered environments
- **Semantic Level**: Understanding task semantics, where to put clothes and shoes (laundry hamper, not on the bed), and what tools are appropriate for cleaning spills
- **Environmental Level**: Adapting to "messy" real-world environments like homes, grocery stores, offices, and hospitals

### Co-Training on Heterogeneous Data

The breakthrough innovation in π₀.₅ is **co-training on heterogeneous data sources**. The model learns from:

1. **Multimodal Web Data**: Image captioning, visual question answering, object detection
2. **Verbal Instructions**: Humans coaching robots through complex tasks step-by-step
3. **Subtask Commands**: High-level semantic behavior labels (e.g., "pick up the pillow" for an unmade bed)
4. **Cross-Embodiment Robot Data**: Data from various robot platforms with different capabilities
5. **Multi-Environment Data**: Static robots deployed across many different homes
6. **Mobile Manipulation Data**: ~400 hours of mobile robot demonstrations

This diverse training mixture creates a "curriculum" that enables generalization across physical, visual, and semantic levels simultaneously.

To use π₀.₅ in your LeRobot configuration, specify the policy type as:

```python
policy.type=pi05
```

## Training

### Local PaliGemma tokenizer

`policy.text_tokenizer_name` accepts a local PaliGemma tokenizer directory or a
Hub ID, for example:

```bash
--policy.text_tokenizer_name=/path/to/paligemma-3b-pt-224
```

The existing default remains `google/paligemma-3b-pt-224`. This default, or
`None`, preserves a saved processor's tokenizer; newly created processors use
the PaliGemma default. A custom path or non-default Hub ID also overrides the
tokenizer when loading saved processors; an explicit
`preprocessor_overrides["tokenizer_processor"]` takes precedence.
This option changes the tokenizer location; use the tokenizer belonging to the
pretrained PaliGemma model, with the same vocabulary and special tokens.

The merge and backend-conversion exports bundle the tokenizer with their
processors and clear the original local-path override. For a training checkpoint
that includes bundled tokenizer artifacts, `--policy.text_tokenizer_name=null`
uses those artifacts after moving to another machine, or set the option to the
corresponding local tokenizer directory on that machine.

### Optional RLinf network backend

For this fork's day-to-day commands, see the [RLT workflow guide](../workflows/rlt/README.md).
[Architecture](../architecture/rlt.md) and [checkpoint/runtime troubleshooting](../troubleshooting/rlt.md)
are maintained separately; the complete tutorial below remains the reference for examples and API details.

Set `policy.backend=rlinf` to use the native PyTorch Gemma/SigLIP network
vendored from RLinf revision `061c4cce80bbab998ef90585475d3f51290a2dfa`.
`policy.backend=lerobot` remains the default. The policy type stays `pi05`;
both backends use the same LeRobot processors, relative-action transforms,
action queue and remote RTC client/server protocol. No RLinf, Ray, Hydra,
OpenPI or JAX installation is needed.

The backend supports ordinary inference, guided/trained RTC, forward training,
gradient checkpointing and PEFT (including the mixed fine-tuning recipe below).
MEM options are rejected explicitly. Use a full PI05 checkpoint without MEM to
compare the backends; merge adapters before converting between backends.
The existing precision profiles are preserved in both backends: `lerobot` keeps
the full visual path in FP32, `openpi` uses selective FP32 embeddings/norms with
a BF16 trunk, and `checkpoint` applies the selected dtype to all VLA parameters.
Euler integration and returned actions stay FP32. The existing
`mask_action_padding_loss` and `use_pretrained_stats` training options remain
available alongside the mixed LoRA recipe.
As in the original backend, `precision_profile=openpi` or enabled compilation
sets FP32 matmul precision to `high`. Fast guided RTC prepares delay-dependent
padding and masks outside the compiled sampler; native/reference RTC uses
separate compiled prefix and denoiser regions when needed.
An ordinary checkpoint does not gain
trained RTC support from conversion: trained RTC still requires
`rtc_training_max_delay > 0` and compatible trained weights.

The integration supports opt-in RLT Stage 1 and the compact Stage 2 actor-critic
with fixed-window replay described below. Native RLT weights require matching
saved structure settings. Other RLinf task-specific heads remain unsupported;
strict loading rejects extra tensors.

To load an existing LeRobot PI05 checkpoint into the new backend:

```python
from dataclasses import replace

from lerobot.configs import PreTrainedConfig
from lerobot.policies.pi05 import PI05Policy

checkpoint = "/path/to/piper_pi05/pretrained_model"
config = replace(PreTrainedConfig.from_pretrained(checkpoint), backend="rlinf")
policy = PI05Policy.from_pretrained(checkpoint, config=config)
```

LeRobot/OpenPI safetensors are converted in memory. Native RLinf `img.*` and
`llm.*` safetensors are also accepted when an explicit matching `PI05Config`
is supplied. Strict loading checks all network weights and shapes. Saving
the resulting policy writes a LeRobot config with `backend="rlinf"` and native
network weights under `model.*`; the source checkpoint is not modified.

For a measured comparison on an existing dataset, run from the repository root:

```bash
uv run examples/tutorial/pi05/compare_backends.py \
    --checkpoint /path/to/piper_pi05/pretrained_model \
    --dataset-repo-id your_name/piper_task \
    --dataset-root /path/to/piper_dataset \
    --frame-index 0 \
    --device cuda \
    --dtype bfloat16 \
    --warmup 2 --iterations 10 \
    --output outputs/pi05_backend_comparison.json \
    --export-dir outputs/piper_pi05_rlinf
```

The source checkpoint must be a LeRobot PI05 checkpoint with saved policy
processors and the normalization stats matching the input dataset. A Hub ID
can be used in place of a local checkpoint; `--revision` pins its revision.
`--dataset-root` can be omitted for a cached/Hub dataset. To use the CPU,
select `--device cpu --dtype float32`.

The tool preprocesses one observation once, creates fixed noise, and loads
the backends sequentially. It reports normalized and executable action errors,
warmup-excluded inference latency, and CUDA peak allocated/reserved memory
(including the loaded model and warmup). Compilation and RTC are disabled
for this baseline comparison. These measurements do not measure robot task
success. Repeat with other frame indices to cover different task phases.

Alternatively, `--batch /path/to/observations.pt` accepts an observation
dictionary saved with `torch.save`. Images use BCHW `[0, 1]` tensors, state
uses `(batch, state_dim)`, and `task` is a list of strings. For already
processed batches, add `--batch-is-preprocessed`; these contain normalized
state and language tokens, while images retain the PI05 policy's `[0, 1]`
input convention. No tokenizer is loaded in that mode unless exporting.

`--export-dir` must be new or empty. It saves the converted policy and both
processors for the existing remote RTC server/client. Keep the client's
policy type `pi05` and point its checkpoint path at the exported directory.
The exported baseline has `rtc_config=None`; the RTC server applies its RTC
settings as usual when loading it.

RLinf intentionally uses exact GELU, while the default backend uses the
OpenPI tanh approximation. Mixed-precision and time-embedding paths also
differ. Output comparisons therefore report errors rather than assert exact
parity. See the
[upstream activation discussion](https://github.com/RLinf/RLinf/issues/1725)
for the GELU difference.

### VLM LoRA with a fully trained action expert

Both backends support `policy.peft_mode=vlm_lora_expert_full`. This recipe adds
LoRA to **vision and language attention plus MLPs**: the language MLP's gate/up/down
projections and the vision MLP's two linear projections. All VLM base weights,
including embeddings, norms and the visual projector, remain frozen. The entire
action expert is trained in full, including its MLPs, adaptive norms, action
input/output projections and time MLPs.

Language and vision LoRA scopes are independent:

| Policy option | Values | Default |
| --- | --- | --- |
| `peft_language_lora` | `none`, `attention`, `attention_mlp` | `attention_mlp` |
| `peft_vision_lora` | `none`, `attention`, `attention_mlp` | `attention_mlp` |

`none` freezes that component completely; `attention` adapts only its attention
projections; `attention_mlp` also adapts its MLP projections. These options apply
to `peft_mode=vlm_lora_expert_full`. The action expert is trained and saved in full
for every combination, including when both sides are `none`.

For example, language Attention + MLP LoRA with frozen vision uses:

```bash
--policy.peft_mode=vlm_lora_expert_full \
--policy.peft_language_lora=attention_mlp \
--policy.peft_vision_lora=none
```

Change only `peft_vision_lora` to `attention` or `attention_mlp` to enable vision
LoRA separately. Both sides use `peft.r` and `peft.lora_alpha` for rank/scaling.

The original LeRobot backend also supports this combination through explicit
`peft.target_modules` and `peft.full_training_modules`; the named recipe provides
the corresponding defaults for either network layout. `peft_mode=default` keeps
the existing action-expert LoRA defaults. Explicit `peft.*` target overrides
replace the recipe's defaults, including the language/vision scope selections.

Older attention-only adapters retain the targets saved in their own
`adapter_config.json` when reloaded. Start a new adapter with this recipe to
include the MLPs; reloading an old adapter does not add new targets.

Install the `pi` and `peft` extras in your existing training environment. Starting
from your normal Piper training command with `--policy.path`, add:

```bash
--policy.backend=rlinf \
--policy.peft_mode=vlm_lora_expert_full \
--policy.peft_language_lora=attention_mlp \
--policy.peft_vision_lora=attention_mlp \
--policy.train_expert_only=false \
--policy.freeze_vision_encoder=false \
--policy.gradient_checkpointing=true \
--peft.method_type=LORA \
--peft.r=16 \
--peft.lora_alpha=32
```

Use `--policy.backend=lerobot` to keep the original network implementation.
Keep the normal dataset, camera names, action semantics, normalization and RTC
training options. An RLinf base with no LeRobot config must first be exported
with a matching `PI05Config` and processors. Do not copy old `peft.target_modules`
or `peft.full_training_modules` into the new command: module names differ between
backends. Both parameter groups use the normal policy learning rate; separate
VLM/expert rates are not introduced by this recipe.

For RLinf's fused vision attention, the adapter uses temporary effective weights
during forward, preserving frozen base weights even in BF16. It also applies each
output-projection update once when permanently merging. The normal `make_policy`
reload path restores this custom PEFT dispatch automatically.
Fused vision attention requires `lora_dropout=0` and `lora_bias=false`.
Unsupported nonzero dropout or LoRA-B bias settings are rejected during wrapping,
reloading and adding adapters, rather than being silently ignored. This does not
restrict dropout in the native language MLP adapter.
The native language MLP adapter applies separate gate/up/down low-rank updates
to activations, preserving RLinf's packed `w_gating`/`w_linear` base weights.
Merging folds these updates back into the native tensors for ordinary inference.

Training checkpoints contain `adapter_model.safetensors` (both the VLM LoRA
weights **and the full trained action expert**), `adapter_config.json`, the
LeRobot `config.json`, both processors and the usual `training_state/`. These
are larger than LoRA-only adapters because the expert is saved in full. Keep
the referenced base checkpoint available: it is required to reload the frozen
VLM. The base Hub revision is stored separately from the adapter revision.
The PI05 factory reload and merge script reject incomplete adapter checkpoints,
including missing LoRA or full-expert tensors, instead of continuing with missing
trained weights.

To continue fine-tuning from the saved model, point `--policy.path` at its
`pretrained_model` directory. To resume the optimizer, scheduler and step too,
use the normal training resume entry point:

```bash
lerobot-train \
    --config_path=outputs/piper_pi05/checkpoints/last/pretrained_model/train_config.json \
    --resume=true
```

Before deployment to the existing Piper/RTC inference server, merge the adapter
and export the full model with its original normalization and relative-action
processors:

```bash
uv run examples/tutorial/pi05/merge_lora.py \
    --adapter outputs/piper_pi05/checkpoints/last/pretrained_model \
    --output-dir outputs/piper_pi05_merged \
    --device cpu
```

The destination must be new or empty. Hub adapters accept `--revision`; their
base uses the revision saved in `adapter_config.json`. The exported directory
contains a full `model.safetensors`, `use_peft=false` and both processors. Point
the existing client/server at this directory with policy type `pi05`. The
export preserves the backend and trained-RTC configuration. BF16 adapter
merging can introduce rounding differences; compare fixed-noise action chunks
before deploying a trained model. An ordinary backend conversion does not train
an RLT encoder or add actor-critic training.

### RLT Stage 1: train, reload, and export RL features

RLT compresses the **final VLM prefix hidden states** into one continuous
`z_rl` vector; it does not tokenize or replace the action expert. This Stage 1
implementation follows RLinf revision `061c4cce80bbab998ef90585475d3f51290a2dfa`.
It does not add the Stage 2 actor-critic, reward, or online replay loop.

Start with a task-trained, full/merged PI05 checkpoint whose saved processors
contain the intended normalization and tokenizer. If it is a LoRA adapter,
first use `merge_lora.py` above. Set `policy.backend=rlinf`; existing backend
conversion numerical considerations still apply.

For **frozen VLA / RLT-only training**, keep your normal dataset, checkpoint,
batch size and training-step arguments, remove the `--peft.*` arguments, and use:

```bash
--policy.backend=rlinf \
--policy.pretrained_path=/path/to/task_trained_merged_pi05 \
--policy.use_rlt=true \
--policy.rlt_training_mode=frozen_vla \
--policy.dtype=float32 \
--accelerator.mixed_precision=bf16 \
--policy.rlt_embed_dim=2048 \
--policy.rlt_prefix_seq_len=1024 \
--policy.rlt_num_layers=2 \
--policy.rlt_num_heads=8 \
--policy.rlt_mlp_ratio=4.0 \
--policy.rlt_image_only=false \
--policy.rlt_use_mask=true \
--use_pretrained_stats=true
```

This mode freezes **all** VLA parameters and keeps those modules in eval mode,
including the action expert and projections. It trains the RLT encoder and
reconstruction decoder; it does not sample flow-matching noise or run the
action expert during training. Its loss is only RLT reconstruction. A training
batch may contain observations alone, although the ordinary dataset pipeline
can still supply actions. No reward labels are needed for Stage 1.
New RLT parameters stay FP32 independently of the VLA precision profile; outer
AMP selects operation precision without changing parameter storage.

`--policy.gradient_checkpointing=true` also checkpoints each RLT encoder and
decoder layer during training, including when the VLA is frozen. It reduces
saved activations by recomputing layers during backward; parameter and optimizer
memory are unchanged. Evaluation and feature extraction do not use checkpointing.

For **joint training with VLM LoRA + full action expert**, keep the existing
mixed recipe and PEFT arguments and add:

```bash
--policy.use_rlt=true \
--policy.rlt_training_mode=joint \
--policy.rlt_alpha=1.0
```

The total loss is `rlt_loss + rlt_alpha * vla_loss`. The RLT objective consumes
detached VLM features, so only the action objective trains VLM LoRA and the
action expert. The whole RLT module is added to PEFT `modules_to_save`, trained
in full, and checked during adapter reload/merge. Existing action padding and
trained-RTC loss masking are retained. RLT loss averages valid tokens/channels
within each sample, then averages samples; `reduction="none"` returns combined
per-sample losses for weighting. `rlt_use_mask=true` excludes missing cameras
and token padding from RLT reconstruction.
Joint training with `rlt_use_mask=false` uses an additional observation-only
prefix pass: otherwise fully masked padding-query features could depend on
the training action sequence. The default masked path reuses the joint pass.

`rlt_prefix_seq_len` must cover the selected prefix: at 224px each camera
contributes 256 image tokens, plus `tokenizer_max_length` when
`rlt_image_only=false`. Three cameras and 200 language/state tokens need 968
positions; four need 1224. Exceeding the configured capacity raises an error.
The input width is inferred from the VLM variant. Structure settings are saved
in `config.json` and must match when loading native RLT weights.

The upstream default module is substantial: at width 2048, two layers per
encoder/decoder, and MLP ratio 4, the pair has about 747 million parameters.
FP32 parameters, gradients and Adam moments alone require about 11.1 GiB before
VLA/activation memory. Smaller `rlt_embed_dim`/`rlt_mlp_ratio` settings are
architecture changes and require training a matching RLT checkpoint.
Joint PEFT training also keeps the ordinary `modules_to_save` frozen copies,
which adds memory beyond this estimate.

Ordinary LeRobot PI05 bases without RLT initialize a new RLT module explicitly
in logs. Checkpoints whose saved config enables RLT must contain its complete
weights; partial or entirely missing RLT weights are errors, including under
non-strict loading. For a bare native base without a LeRobot config, the Python
loading API requires `initialize_rlt=True` to distinguish initialization from a
damaged trained checkpoint.

Use the normal `lerobot-train` checkpoint/resume mechanism. Retain the original
adapter base when joint training uses PEFT. Export either kind of Stage 1
checkpoint to a self-contained inference directory:

```bash
python examples/tutorial/pi05/export_rlt.py \
    --checkpoint outputs/piper_rlt_stage1/checkpoints/last/pretrained_model \
    --output-dir outputs/piper_rlt_inference \
    --device cpu
```

This merges adapters if present and saves the full VLA, RLT encoder, and both
processors/tokenizer. It removes the reconstruction decoder and records
`rlt_inference_only=true`. Such an export supports ordinary Piper/RTC action
inference and feature extraction, and rejects Stage 1 training; keep the full
training checkpoint to resume. `merge_lora.py --rlt-encoder-only` provides the
same export for a joint PEFT checkpoint.

```python
from lerobot.policies.factory import make_pre_post_processors
from lerobot.policies.pi05 import PI05Policy

path = "outputs/piper_rlt_inference"
policy = PI05Policy.from_pretrained(path)
pre, post = make_pre_post_processors(policy.config, pretrained_path=path)
batch = pre(raw_observation_batch)
z_rl = policy.extract_rlt_features(batch)  # (batch_size, rlt_embed_dim)
actions = post(policy.predict_action_chunk(batch))
```

The independent feature/action APIs each run their own prefix pass.
`predict_action_chunk_with_rlt_features(batch)` returns `(reference_chunk, z_rl)`
from a single prefix pass for the fixed-window Stage 2 adapter below.
Stage 1 validation uses real miniature networks, masks and gradients, saved
processor round trips, optimizer resume, full/PEFT reload and encoder-only
export. Full-size task training and Piper success rates require a separate run.

Validation uses miniature real networks with gradient updates, checkpoint
save/resume, adapter reload and merged action comparisons. It does not establish
full-size training memory requirements or task success on a real Piper.

### RLT Stage 2: actor-critic and fixed execution-window replay

`rlt_actor` is a small trainable policy over frozen Stage 1 features. The
`rlt_ac` algorithm plugs into the existing algorithm factory and `RLTrainer`.
Its objective follows the [RLinf RLT actor-critic route](https://github.com/RLinf/RLinf/blob/061c4cce80bbab998ef90585475d3f51290a2dfa/rlinf/workers/actor/fsdp_rlt_ac_policy_worker.py):
the actor minimizes `-q_weight * Q1 + bc_weight * BC`; twin target critics use
their minimum Q. Normal steps use the VLA reference as the BC target; human
intervention steps use the recorded executed command. Reference dropout is
applied only to the actor input. There is no entropy-temperature optimizer.

The actor outputs **10 policy steps** by default. Its tanh actions and replay
actions use the saved Stage 1 normalized action coordinates. The actor observes
the first 10 reference rows, the RL token and normalized proprioception. The
critics observe the token, proprioception and a complete K-step action; realized
duration is not an input to Q. The feature dictionary uses these LeRobot names:

| Field | Unbatched shape | Meaning |
| --- | --- | --- |
| `observation.rlt` | `(z_dim,)` | Frozen Stage 1 `z_rl` |
| `observation.state` | `(proprio_dim,)` | Stage 1-normalized state |
| `observation.reference_chunk` | `(reference_horizon, action_dim)` | Normalized VLA reference |

**Execution windows.** `FixedWindowRollout` commits one window and accepts no
mid-window reference replacement. After the window, one new observation supplies
both the previous transition's `next_state` and the next window's `state`.
This is a separate synchronous collection API. The normal asynchronous RTC
client, its splicing/compilation path, and Piper driver modes are unchanged.
The shared Stage 2 feature/reference call is eager and uses `rtc_config=None`;
the Stage 1 weights can retain their trained-RTC training configuration.

Replay stores **controller-reported sent commands**, including smoothing,
clipping or human takeover, rather than an unexecuted predicted suffix. A command
is not a measurement of the reached joint position. Absolute commands are mapped
back to normalized coordinates with the window's original relative-action anchor.
There is no second normalization of `z_rl` or proprioception on the learner.

Each transition carries per-policy-step rewards. For `n` executed steps, the
target is `sum(gamma**i * reward[i]) + (1-terminated) * gamma**n * min(Q_target)`.
Motor interpolation substeps do not multiply `n`. Early termination or a time
limit zero-pads unexecuted action receipts and rewards. The valid-step mask
controls rewards, discounting and BC; Q retains the planned tail as context.
A time limit still bootstraps and must provide the **final pre-reset observation**. Cancellation,
disconnect, an invalid reward, or a failed capture drops the partial window and
requires a fresh `begin_episode`; those events do not manufacture terminal data.

**Freeze and version the feature model.** Export/merge Stage 1 first. Stage 2 uses
the tokenizer bundled with the saved processors, even when `text_tokenizer_name`
still points to the original external directory. Legacy processors without a
tokenizer bundle must be re-exported. A local fingerprint streams weights,
configs, normalization assets and every bundled tokenizer file once; tokenizer
directory symlinks must be materialized. Hub inputs require a full commit revision.
The loader checks this identity against the actor/replay configuration, and each
sampled batch carries its digest. Changing
the feature model or processors requires new replay and a matching actor config.
Direct construction from an in-memory model is available for tests/adapters; its
caller must supply the same immutable identity contract.

The feature fingerprint now uses the v2 namespace. Recompute the actor config's
`feature_model_id` and collect new replay after this update. Previous fingerprints
cannot establish which external tokenizer produced old features, so the frozen
feature loader rejects old actor/replay identities rather than relabeling them.

```python
from threading import Event

from lerobot.configs import PreTrainedConfig
from lerobot.policies.rlt_actor import RLTActorConfig, RLTActorPolicy
from lerobot.rl.rlt.features import FrozenRLTFeatures, checkpoint_fingerprint
from lerobot.rl.rlt.replay import FixedWindowReplayBuffer
from lerobot.rl.rlt.rollout import FixedWindowRollout, RobotWindowStep

stage1 = "/path/to/piper_rlt_inference"
source = PreTrainedConfig.from_pretrained(stage1)
cfg = RLTActorConfig(
    feature_model_id=checkpoint_fingerprint(stage1),
    z_dim=source.rlt_embed_dim,
    proprio_dim=source.input_features["observation.state"].shape[0],
    action_dim=source.output_features["action"].shape[0],
    execution_horizon=10,
    reference_horizon=source.chunk_size,
    device="cuda",
    push_to_hub=False,
)
features = FrozenRLTFeatures.from_pretrained(stage1, cfg, device="cuda")
actor = RLTActorPolicy(cfg).to("cuda")
replay = FixedWindowReplayBuffer(cfg, capacity=100_000)
stop = Event()
rollout = FixedWindowRollout(features, replay, actor=actor, stop_event=stop)
```

For an **already connected, exclusively owned** `RobotIO`, provide application
callbacks `prepare(raw)` and `task_reward(raw, sent_command)`. `prepare` must
produce the saved PI05 processor's raw batch convention: float images in `[0,1]`,
state, and task. `task_reward` returns `RewardSignal(reward, terminated, truncated,
intervention)` from the real task outcome. It is not a learned/default reward model.

```python
# io, prepare and task_reward are supplied by the robot/environment application.
step = RobotWindowStep(
    io, prepare, task_reward,
    action_names=source.action_feature_names,
    fps=30, stop_event=stop,
)
raw, _, _ = io.capture(0.2)
rollout.begin_episode(prepare(raw), episode_id=0)
transition = rollout.collect_window(step, use_actor=False)  # Initial VLA/reference collection.
replay.save("outputs/piper_rlt_replay.pt")
```

`RobotWindowStep` validates the checkpoint/robot action order and records the
return value of `io.send`, followed by a fresh post-command observation and its
reward. It does not connect, reset or home hardware. Call it once per policy
interval; applications with their own interpolation or human correction return
one `ExecutedStep` with the actual command and reward for that policy interval.
The bridge passes a stop signal and a command deadline bounded by
`max_observation_age_s`. RobotIO and DaggerRobotIO check these after acquiring the
motor lock, immediately before the driver write. This rejects queued commands;
it cannot undo a write the driver has already started.
An episode end requires an application reset and a new `begin_episode` call.
After training and evaluating actor weights, `use_actor=True` selects that actor
for the next full window. Do not run this collector alongside another controller
that owns the same arm.

**Train the small learner from collected replay**, without loading VLA weights
or opening any robot connection:

```bash
python examples/tutorial/pi05/train_rlt_stage2.py \
    --replay outputs/piper_rlt_replay.pt \
    --output-dir outputs/piper_rlt_stage2_0001 \
    --device cuda --steps 1000 --batch-size 256

python examples/tutorial/pi05/train_rlt_stage2.py \
    --resume outputs/piper_rlt_stage2_0001 \
    --output-dir outputs/piper_rlt_stage2_0002 \
    --device cuda --steps 1000 --batch-size 256
```

`steps` counts additional learner updates. Output directories must be new. Small
actor/critic heads train in FP32 independently of the VLA precision profile and
outer AMP. Checkpoints include actor weights/config, critics and targets, both
optimizers, update step, replay ring and sampling RNG, and Python/Torch RNG.
Replay v2 saves a complete `planned_action` separately from the actual executed
`action` receipts. The critic always values a full K-step action: actual sent
rows replace the plan's executed prefix, and unexecuted planned rows remain
context only. Realized duration is used for rewards, discounting and BC masks;
it is not an input to Q. This keeps short successful windows and full-window
TD backups in the same value-function domain. Unexecuted receipt/reward tails
remain zero padded.

Legacy v1 replay containing only complete windows upgrades automatically. Old
partial windows lack their unexecuted plan and must be recollected. The earlier
critics/optimizer checkpoints cannot resume this corrected critic layout; retain
the actor through an explicit warm start with compatible replay:

```bash
python examples/tutorial/pi05/train_rlt_stage2.py \
    --replay outputs/new_rlt_replay.pt \
    --actor-checkpoint outputs/old_rlt_checkpoint/actor \
    --output-dir outputs/rlt_corrected_0001 --device cuda --steps 1000
```

This starts fresh critics/optimizers and preserves the saved actor dimensions
and exploration settings. Corrected v2 checkpoints resume normally using
`--resume`.
Actor checkpoint loading is strict: missing or foreign tensors abort resume
before optimizer restoration. Replay stores latent features and actions, not
camera images. `algorithm.get_weights()`
returns an actor-only payload with feature identity and learner version. The
single rollout owner calls `rollout.load_actor_weights(algorithm.get_weights())`
between windows; this checks the complete snapshot before replacing parameters,
rejects stale versions and records the loaded version in replay. Calls made
during a window are rejected. This implementation does not
add a distributed actor-weight/reward RPC service or an automatic online learner
to the ordinary RTC server.

Validation uses real miniature PI05/RLT networks, actual `RLTrainer` updates,
per-step rewards/masks, relative-action round trips, cancellation/reset fencing,
and exact checkpoint resume. It verifies software contracts, not Piper task
success or full-size inference latency. This is a local RLT implementation;
native RLinf Stage 2 MLP checkpoints are not interchangeable with its parameter
layout, and sharded Stage 2 training is not validated.

### Stage 3: RLT with overlapping remote RTC execution

This opt-in mode uses the existing `policy_server_deployment` and
`robot_client_deployment` entrypoints. Ordinary deployment and its JSON settings
keep their current behavior when `rlt.enabled=false` (the default). DAgger,
ReCAP, trained RTC and distributed online learner/weight broadcasts are not
part of this mode. Training remains the replay CLI described below.

**Execution contract.** Each nonterminal replay window still contains **10 policy
actions**, independently of motor interpolation. With `rlt.prefix_steps=3`, the
next boundary observation is captured after action 10. The client uploads that
observation and the previous window's actual command/reward receipts, then
executes 3 already committed continuation rows while the server computes the
new reference, RLT feature and actor output. The new result must arrive within
the 3-step budget. The client uses its remaining 7 rows to finish the window.

The continuation is the frozen VLA reference's `[10:13]` tail from the previous
plan. It is **not an additional actor prediction**. When loaded, the actor owns
7 new rows per steady-state window and all 10 rows of the cold first window.
Without an actor, those rows use the frozen VLA reference. The handover from an
actor to a VLA continuation needs task evaluation. Changing `prefix_steps`
changes this tradeoff. This is a local RLT
RTC adaptation, not a claim of identical upstream RLinf online RTC semantics.

The state gains `observation.rtc_prefix` and `observation.rtc_prefix_mask`.
The actor clamps committed rows and receives that context; the critic also
sees the reference that determines the next continuation. Actor Q/BC updates
exclude committed rows, and a batch containing only such rows skips the actor
update. Replay uses actual reported commands in the **original window's**
normalization and relative-action coordinates. Each window owns a coordinate
snapshot, so the next inference cannot overwrite its anchor. A boundary's
state is shared exactly by the preceding transition's next state and the
following transition's current state. Termination and truncation stay distinct.

The server uses the tokenizer/normalization assets bundled in the Stage 1
checkpoint. The Stage 1 checkpoint must be full/merged RLinf PI05 with RLT,
and must save `action_feature_names` in robot action order. Its chunk must cover
`execution_horizon + prefix_steps`. RLT retains the saved numerical profile;
the deployment compile flag/mode control compilation. Features and reference
share one VLM prefix pass, and guided RTC conditions the reference on the
committed absolute prefix after reanchoring to the new observation.

Startup performs two motion-free dry warmups and at least one measured dry
request, including the continuation path. No dry request enters replay. The
maximum measured round trip must fit `prefix_steps / fps - budget_margin_s`.
At 30 Hz and 3 steps the default budget is 95 ms. If it does not fit, reduce
latency, increase `prefix_steps` while keeping it below 10, or lower both
client/server policy fps. A live overrun aborts execution at the committed
prefix; the client never extends it or silently replays a partial window.
Before each prefix policy step starts, the client checks for an already completed
inference failure and aborts the remaining policy steps. This check does not run
inside motor interpolation substeps: a failure arriving during a policy step is
handled before the next policy step starts. The cold
first plan must start within `observation_max_age_s` measured from the oldest
initial sensor timestamp, including inference and motor-lock waiting; expiry
rejects actuation even if the RPC request timeout has not elapsed.
Final-state encoding after a real task boundary waits without sending more
commands. Reset fences the generation, drops unfinished data and keeps the
existing planned Piper reset/homing path. Delayed results cannot actuate the
next episode. Task changes require ending/resetting the RLT rollout first.

For example, add these **overrides to the current deployment configuration**:

```bash
# Inference server; paths are on this host. Omit actor_checkpoint initially
# to collect frozen-VLA reference rollouts; no randomly initialized actor executes.
python -m lerobot.async_inference.server.policy_server_deployment \
  --config_path=src/lerobot/async_inference/config/policy_server_deployment.json \
  --rlt.enabled=true --rlt.execution_horizon=10 --rlt.prefix_steps=3 \
  --rlt.replay_dir=outputs/piper_rlt_rtc \
  --rlt.actor_checkpoint=/server/checkpoints/rlt_rtc/actor

# Robot client; pretrained_name_or_path is the Stage 1 path ON THE SERVER.
# Keep the existing Piper, cameras, task, fps and interpolation settings.
python -m lerobot.async_inference.client.robot_client_deployment \
  --config_path=src/lerobot/async_inference/config/robot_client_deployment.json \
  --pretrained_name_or_path=/server/checkpoints/pi05_rlt_stage1 \
  --rlt.enabled=true --rlt.execution_horizon=10 --rlt.prefix_steps=3 \
  --rlt.reward_provider=manual
```

The RLT `prefix_steps` setting is independent of ordinary `rtc.execution_horizon`
(which may currently be 20). Both sides must use the same RLT window/prefix and
policy fps. Current server/client configurations must use `rtc.mode=guided` /
`rtc_mode=guided` for RLT. The saved Stage 1 numerical profile is used directly;
ordinary `pi05_inference.profile` overrides are not applied to frozen features.

With `reward_provider=manual`, `/start` begins an episode; `/success` supplies
reward 1 and termination, `/failure` supplies reward 0 and termination, and
`/truncate` supplies reward 0 and time-limit truncation. Other executed
intervals get reward 0. Feedback is consumed on a policy interval; `/reset`
discards unfinished data rather than inventing a success or failure label.
A task-specific callback can instead be configured as `module:function`; it
receives `(raw_post_step_observation, actual_absolute_command)` and returns
`lerobot.rl.rlt.rollout.RewardSignal`. Import/validation happens before robot
connection. The robot must report its actual sent command; a missing report
is an error. Built-in human takeover/DAgger control is not connected here.

The server atomically journals **completed windows** to
`outputs/piper_rlt_rtc/<session_uuid>/g..._s....pt`. Saving one small shard at a
time avoids serializing the entire live ring on every refill. Use one session
directory (or a normal replay file) with the same learner:

```bash
python examples/tutorial/pi05/train_rlt_stage2.py \
  --replay outputs/piper_rlt_rtc/SESSION_UUID \
  --output-dir outputs/rlt_rtc_0001 --device cuda --steps 1000 --batch-size 256

python examples/tutorial/pi05/train_rlt_stage2.py \
  --resume outputs/rlt_rtc_0001 \
  --output-dir outputs/rlt_rtc_0002 --device cuda --steps 1000 --batch-size 256
```

Load the resulting `outputs/rlt_rtc_0002/actor` on the next deployment run and
set `rlt.actor_version` to identify its learner version in new replay. The new
RTC actor has additional inputs and its replay includes a distinct
`rtc_prefix_steps` specification. Stage 2 replay/full optimizer checkpoints
cannot be resumed as RTC data. An existing matching Stage 2 actor can be used
for explicit **policy-only** initialization by adding
`--rlt.warmstart_stage2_actor=true` on the server. Its existing weights are
copied and the appended first-layer input columns start at zero; RTC
critics/optimizers still start fresh. RTC checkpoints resume normally with
their RTC replay specification. Native upstream Stage 2 weights are not
interchangeable with this local actor layout.

Validation includes real local gRPC client/server execution with a mock robot,
policy-versus-motor step counts, actual receipt alignment, late inference,
reset while waiting for motor ownership, journal training/resume, miniature
PI05/RLT guided-sampler parity and CUDA Inductor compilation. It does not
establish Piper task success or full-model latency on the target server.

### Quickstart on LIBERO

Finetune the LIBERO base model on [lerobot/libero](https://huggingface.co/datasets/lerobot/libero), a ~1.9 GB video-encoded copy of the demonstrations behind the [results below](#libero-benchmark-results).

It carries the keys π₀.₅ reads, which are also the ones the LIBERO environment produces at evaluation time:

| Feature                     | Shape in the dataset | How π₀.₅ consumes it                                    |
| --------------------------- | -------------------- | ------------------------------------------------------- |
| `observation.images.image`  | 256×256×3, agentview | resized to 224×224                                      |
| `observation.images.image2` | 256×256×3, wrist     | resized to 224×224                                      |
| `observation.state`         | 8                    | discretized into 256 bins and written into the prompt   |
| `action`                    | 7                    | padded to 32 internally; the loss uses the first 7 dims |

**No `--rename_map` is needed here** — the keys already match; see [Rename Map and Empty Cameras](./rename_map) if yours differ.

<Tip>
  π₀.₅ uses the gated
  [google/paligemma-3b-pt-224](https://huggingface.co/google/paligemma-3b-pt-224)
  tokenizer — accept its license on the Hub and log in with `hf auth login`
  before training.
</Tip>

Sized for a single 80 GB GPU:

```bash
lerobot-train \
    --dataset.repo_id=lerobot/libero \
    --policy.type=pi05 \
    --policy.pretrained_path=lerobot/pi05_libero_base \
    --policy.normalization_mapping='{"ACTION": "MEAN_STD", "STATE": "MEAN_STD", "VISUAL": "IDENTITY"}' \
    --policy.n_action_steps=10 \
    --policy.empty_cameras=1 \
    --policy.freeze_vision_encoder=false \
    --policy.train_expert_only=false \
    --policy.gradient_checkpointing=true \
    --policy.dtype=bfloat16 \
    --policy.device=cuda \
    --policy.push_to_hub=false \
    --output_dir=./outputs/pi05_libero \
    --job_name=pi05_libero \
    --batch_size=64 \
    --num_workers=8 \
    --steps=30000 \
    --save_freq=5000 \
    --seed=1000
```

**Mean/std normalization, not π₀.₅'s [quantile default](#quantile-statistics)** — matching [pi05_libero_finetuned_v044](https://huggingface.co/lerobot/pi05_libero_finetuned_v044), the checkpoint the results below were measured on.

**`--policy.n_action_steps=10` and `--policy.empty_cameras=1` are explicit** because `--policy.pretrained_path` loads weights only — `lerobot/pi05_libero_base` stores both, and they would otherwise fall back to `50` and `0` (see [Loading a checkpoint](#loading-a-checkpoint)).

Then evaluate a checkpoint with `lerobot-eval` and compare against the reference success rates — see [LIBERO](./libero).

### Quantile statistics

π₀.₅ normalizes `STATE` and `ACTION` with quantiles, so your dataset's `meta/stats.json` needs `q01` and `q99`. Older datasets carry only `min`/`max`/`mean`/`std` and fail on the first batch:

```
ValueError: QUANTILES normalization mode requires q01 and q99 stats
```

Recompute them:

```bash
lerobot-edit-dataset \
    --repo_id your_dataset \
    --new_repo_id your_dataset \
    --operation.type recompute_stats \
    --operation.overwrite true
```

**The result lands in `$HF_LEROBOT_HOME/your_dataset`**, not the cache `--dataset.repo_id` reads — so train with `--dataset.root=$HF_LEROBOT_HOME/your_dataset`, or add `--push_to_hub true` above.

Or keep the dataset as-is and pass `--policy.normalization_mapping='{"ACTION": "MEAN_STD", "STATE": "MEAN_STD", "VISUAL": "IDENTITY"}'`.

Recording, resuming, and merging aggregate quantiles from per-episode summaries, so `meta/stats.json` ends up holding a conservative envelope (`min` for `q <= 50`, `max` for `q > 50`) rather than whole-dataset quantiles. To estimate the latter, scan every episode with a running histogram:

```bash
python src/lerobot/scripts/augment_dataset_quantile_stats.py \
    --repo-id=your_dataset \
    --overwrite \
    --skip-images
```

`--skip-images` keeps the existing image statistics and avoids video decoding when only `STATE`/`ACTION` need recomputing, and `--root` reads a local dataset instead of the Hub. These values are histogram estimates, subject to discretization and rebinning error, so they can differ from the conservative ones — which changes π₀.₅'s normalized targets and therefore its loss scale. Statistics already saved inside an existing checkpoint are not affected.

### Training Command Example

The same finetune with the VLM frozen: less memory, at some cost in success rate. Swap `--dataset.repo_id` for your own dataset.

```bash
lerobot-train \
    --dataset.repo_id=lerobot/libero \
    --policy.type=pi05 \
    --policy.pretrained_path=lerobot/pi05_libero_base \
    --policy.normalization_mapping='{"ACTION": "MEAN_STD", "STATE": "MEAN_STD", "VISUAL": "IDENTITY"}' \
    --policy.n_action_steps=10 \
    --policy.empty_cameras=1 \
    --policy.freeze_vision_encoder=true \
    --policy.train_expert_only=true \
    --policy.gradient_checkpointing=true \
    --policy.dtype=bfloat16 \
    --policy.device=cuda \
    --policy.push_to_hub=false \
    --output_dir=./outputs/pi05_libero_expert \
    --job_name=pi05_libero_expert \
    --batch_size=64 \
    --num_workers=8 \
    --steps=30000 \
    --save_freq=5000 \
    --seed=1000
```

### Key Training Parameters

- **`--policy.compile_model=true`**: Enables model compilation for faster training
- **`--policy.gradient_checkpointing=true`**: Reduces memory usage significantly during training
- **`--policy.dtype=bfloat16`**: Use mixed precision training for efficiency
- **`--batch_size=64`**: Batch size for training, adapt this based on your GPU memory
- **`--policy.pretrained_path=lerobot/pi05_base`**: The base π₀.₅ model you want to finetune, options are:
  - [lerobot/pi05_base](https://huggingface.co/lerobot/pi05_base)
  - [lerobot/pi05_libero_base](https://huggingface.co/lerobot/pi05_libero_base) (specifically trained on the Libero dataset)

### EMA of the policy weights

OpenPI maintains an exponential moving average of the weights during training (`ema_decay=0.99` by default) and keeps the EMA copy for inference. To reproduce this with the LeRobot trainer, add `--ema.enable=true --ema.decay=0.99` to your training command:

```bash
uv run lerobot-train \
  --policy.type=pi05 \
  --dataset.repo_id=your_org/your_dataset \
  --policy.push_to_hub=false \
  --ema.enable=true \
  --ema.decay=0.99
```

Checkpoints contain a directly loadable copy of the EMA weights in `pretrained_model_ema/` next to the live weights. The shadow keeps a full extra copy of the parameters on the GPU. Like OpenPI (which disables EMA in its LoRA configs), EMA is not supported together with PEFT adapters.

### Optional training-time RTC

Pi05 can optionally learn action-prefix conditioning for efficient
[Real-Time Chunking](./rtc), following
[Training-Time Action Conditioning for Efficient Real-Time Chunking](https://arxiv.org/abs/2512.05964).
Set `policy.rtc_training_max_delay` to the largest expected inference delay in
controller steps:

```bash
lerobot-train \
    --dataset.repo_id=${HF_USER}/my_dataset \
    --policy.type=pi05 \
    --policy.pretrained_path=lerobot/pi05_base \
    --policy.rtc_training_max_delay=10 \
    --policy.dtype=bfloat16 \
    --policy.device=cuda \
    --batch_size=8 \
    --steps=30000 \
    --output_dir=outputs/pi05_rtc \
    --job_name=pi05_rtc
```

The default is `0`, which disables training-time RTC and leaves the standard
Pi05 objective unchanged. The configured delay must be smaller than
`chunk_size`. During training, Pi05 samples a clean prefix length independently
for each example and computes flow loss only on the remaining postfix.

Use the resulting checkpoint with trained RTC explicitly:

```bash
lerobot-rollout \
    --strategy.type=base \
    --policy.path=outputs/pi05_rtc/checkpoints/last/pretrained_model \
    --inference.type=rtc \
    --inference.rtc.mode=trained \
    --inference.rtc.execution_horizon=10 \
    --robot.type=so100_follower \
    --robot.port=/dev/ttyACM0 \
    --task="pick up the cube" \
    --fps=50 \
    --device=cuda
```

Set `inference.rtc.execution_horizon` between the checkpoint's
`rtc_training_max_delay` and `chunk_size - rtc_training_max_delay`, and
`inference.queue_threshold` to at least `rtc_training_max_delay`. A one-off
latency spike past the trained range discards that chunk and retries; rollout
stops with an explicit error only if the delay stays out of range. The default
`--inference.rtc.mode=guided` remains available for ordinary checkpoints.

### Loading a checkpoint

The two forms are not interchangeable:

|                                        | `--policy.path`                                | `--policy.pretrained_path`                |
| -------------------------------------- | ---------------------------------------------- | ----------------------------------------- |
| Loads                                  | weights **and** the checkpoint's `config.json` | weights only                              |
| Feature names                          | from the checkpoint                            | from your dataset, after `--rename_map`   |
| Stored settings, e.g. `n_action_steps` | inherited                                      | reset to the defaults                     |
| `--policy.type`                        | must be omitted                                | required                                  |
| `--rename_map`                         | needed when your camera keys differ            | supported for canonicalizing dataset keys |

Use `--rename_map` with either loading form when raw dataset feature names differ from the policy
feature names. For example, the RoboMME fine-tuning command maps its raw `image`, `wrist_image`,
`state`, and `actions` columns while initializing weights with `--policy.pretrained_path`.

### Training Parameters Explained

| Parameter               | Default | Description                                 |
| ----------------------- | ------- | ------------------------------------------- |
| `freeze_vision_encoder` | `false` | Do not freeze the vision encoder            |
| `train_expert_only`     | `false` | Do not freeze the VLM, train all parameters |

**💡 Tip**: Setting `train_expert_only=true` freezes the VLM and trains only the action expert and projections, allowing finetuning with reduced memory usage.

## Short-Horizon Observation Memory (MEM)

Pi05 can optionally use short-horizon visual and proprioceptive context based on
[MEM](https://arxiv.org/abs/2603.03596). Both paths are disabled by default, so
existing checkpoints and training commands retain the single-frame Pi05 behavior.

<Tip warning={true}>

This implements MEM's short-horizon memory only — the video encoder of section
III-C and the proprioceptive projection of section III-D. MEM's long-horizon
_language_ memory (section III-B), in which a high-level policy predicts the next
subtask and a compressed natural-language summary of what has happened so far, is
not implemented. In the paper's ablations, video memory alone recovers only part
of full MEM's task progress on long-horizon tasks.

Introducing memory when finetuning from a checkpoint that was pretrained without
it also corresponds to the paper's weaker `MEM-Posttrain-Only` ablation. MEM's
headline results come from pretraining the video encoder on a diverse mixture of
robot and non-robot video, which no public Pi05 checkpoint currently provides.

</Tip>

Enable it while finetuning with:

```bash
lerobot-train \
    --dataset.repo_id=your_dataset \
    --policy.type=pi05 \
    --policy.pretrained_path=lerobot/pi05_base \
    --policy.use_visual_memory=true \
    --policy.memory_frames=6 \
    --policy.memory_stride=30 \
    --policy.memory_temporal_attention_every=4 \
    ...
```

`memory_frames` includes the current observation. `memory_stride` is measured in
**dataset frames**, not seconds, so scale it with your dataset's `fps`: MEM
pretrains on six observations one second apart, which is `memory_stride=30` for a
30 fps dataset (the default) but `memory_stride=10` for a 10 fps dataset such as
`lerobot/robomme`.

Every fourth SigLIP layer replaces its attention with MEM's composed space-time
attention: causal temporal attention between matching patch tokens, composed with
the standard spatial attention and reusing the pretrained projections, so no
learnable parameters are added to the vision tower. Past-frame tokens are dropped
once the last such layer has run, keeping the downstream language/action prefix
length unchanged.

Unavailable history at the beginning of an episode is padded and masked. At
inference, Pi05 maintains the same strided image history internally and clears
it whenever the policy is reset.

Historical proprioception is an independent option:

```bash
--policy.use_proprioceptive_memory=true
```

When enabled, one projected continuous state token is added for each retained
frame, and the discretized state is removed from the text prompt so the state is
represented exactly once (MEM section III-D). This changes the prompt format, so
enable it from the start of training rather than partway through. Visual and
proprioceptive memory use the same `memory_frames` and `memory_stride` settings,
but either path can be enabled independently. Train or finetune with the selected
memory options; enabling them only at inference does not give a single-frame
checkpoint learned memory behavior.

Under PEFT, `proprio_history_proj` is trained and saved in full via
`modules_to_save`, since it has no pretrained weights to adapt.

At inference, MEM keeps one batched history queue and assumes every batch row
shares episode boundaries. `lerobot-eval` satisfies this by calling
`policy.reset()` before each batched rollout and before resetting the vector
environment. Independently autoresetting rows in an asynchronous vector batch
is not supported; start a new rollout so the complete policy and action queues
are reset together.

## Relative Actions

By default, π₀.₅ predicts absolute actions. You can enable **relative actions** so the model predicts offsets relative to the current robot state. This can improve training stability for certain setups.

To use relative actions, first recompute your dataset stats in relative space via the CLI:

```bash
lerobot-edit-dataset \
    --repo_id your_dataset \
    --operation.type recompute_stats \
    --operation.relative_action true \
    --operation.chunk_size 50 \
    --operation.relative_exclude_joints "['gripper']" \
    --push_to_hub true
```

Or equivalently in Python:

```python
from lerobot.datasets import LeRobotDataset, recompute_stats

dataset = LeRobotDataset("your_dataset")
recompute_stats(dataset, relative_action=True, chunk_size=50, relative_exclude_joints=["gripper"])
dataset.push_to_hub()
```

The `chunk_size` should match your policy's `chunk_size` (default 50 for π₀.₅). `relative_exclude_joints` lists joint names that should remain in absolute space (e.g. gripper commands). Use `--push_to_hub true` to upload the updated stats to the Hub.

Then train with relative actions enabled:

```bash
lerobot-train \
    --dataset.repo_id=your_dataset \
    --policy.type=pi05 \
    --policy.use_relative_actions=true \
    --policy.relative_exclude_joints='["gripper"]' \
    ...
```
