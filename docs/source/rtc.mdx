# Real-Time Chunking (RTC)

Real-Time Chunking (RTC) allows large, flow-matching based robotic policies, such as [Pi0](./pi0), [Pi0.5](./pi05), and [SmolVLA](./smolvla), to produce smooth, continuous, and reactive motion despite having high inference latency. LeRobot provides the original inference-time guided mode and, for compatible Pi05 checkpoints, training-time action conditioning with cheap hard-prefix inference.

These policies generate chunks of future actions (e.g., 50 steps at a time) instead of single actions.
Because the models are large, producing each chunk takes longer than the time it takes the robot to execute it.
Naively executing chunks leads to problems such as pauses, jerky transitions, or sudden changes in strategy whenever the next chunk arrives late or disagrees with the previously executed actions.

RTC solves this by asynchronously generating the next chunk while the robot continues executing the current one, and by guiding the new chunk so it aligns smoothly with the portion of the previous chunk that has already been executed.

## How RTC Works (simplified)

RTC lets the robot think ahead while it’s still moving. When the robot is carrying out one chunk of actions, RTC starts creating the next chunk early.
But since the robot has already moved a bit by the time the new chunk is ready, RTC has to make sure the new chunk still lines up smoothly with what the robot is currently doing.

To do this, RTC treats the beginning of the new chunk like an inpainting or “fill-in-the-gaps” problem:
it gently adjusts the first part of the new chunk so it blends naturally with the robot’s ongoing motion. The result is no pauses, no sudden jumps.

In technical terms, RTC adds a guidance term to the flow-matching denoising process that forces the overlapping timesteps of the new chunk to stay close to the executed portion of the previous chunk, typically using a soft transition mask.

## Quick Start

### Installation

RTC is built into LeRobot. Just install the policy dependencies you need:

```bash
# For Pi0 or Pi0.5
pip install -e ".[pi]"

# For SmolVLA
pip install -e ".[smolvla]"
```

### Using RTC with Pi0

You can use `lerobot-rollout --strategy.type=base --inference.type=rtc` for RTC deployment on real robots.
The snippet below provides a simplified pseudo-example of how RTC operates with Pi0 in your pipeline:

```python
from lerobot.policies.pi0 import PI0Policy, PI0Config
from lerobot.configs import RTCAttentionSchedule
from lerobot.policies.rtc import RTCConfig, ActionQueue

# Load Pi0 with RTC enabled
policy_cfg = PI0Config()

# Enable RTC
policy_cfg.rtc_config = RTCConfig(
    enabled=True,
    execution_horizon=10,  # How many steps to blend with previous chunk
    max_guidance_weight=10.0,  # How strongly to enforce consistency
    prefix_attention_schedule=RTCAttentionSchedule.EXP,  # Exponential blend
)

# Load the policy
policy = PI0Policy.from_pretrained("lerobot/pi0_base", policy_cfg=policy_cfg, device="cuda")

# Now use predict_action_chunk with RTC parameters
inference_delay = 4  # How many steps of inference latency, this value should be calculated based on the inference latency of the policy

# Initialize the action queue
action_queue = ActionQueue(policy_cfg.rtc_config)

# Start in a separate thread with the following function
def get_actions():
  while True:
    if should_get_actions:

      prev_actions = action_queue.get_left_over()
      obs = get_robot_observations(robot)

      # Generate actions WITH RTC
      actions = policy.predict_action_chunk(
          obs,
          inference_delay=inference_delay,
          prev_chunk_left_over=prev_actions,
      )

      action_queue.merge(
          actions, actions, inference_delay
      )

for step in range(num_steps):
    action = action_queue.get()

    # Execute the first N actions
    execute_actions(action)
```

## Key Parameters

`RTCConfig` has the following parameters to tune:

**`mode`** selects the action-prefix conditioning method:

- `guided` (default) applies the original Jacobian guidance during denoising and works with ordinary flow-matching checkpoints.
- `trained` hard-inpaints the previous chunk's prefix with per-action flow timesteps. It currently requires a Pi05 checkpoint trained with `policy.rtc_training_max_delay > 0` and avoids the guidance backward pass.

For trained mode, both `execution_horizon` and the rollout backend's
`inference.queue_threshold` must be at least the checkpoint's
`rtc_training_max_delay`, and `execution_horizon` must not exceed
`chunk_size - rtc_training_max_delay` (the `d <= s <= H - d` bound from the RTC
paper); rollout validates this before connecting the robot.

**`execution_horizon`**: How many timesteps from the previous chunk to maintain consistency with. Higher values mean smoother transitions but potentially less reactivity.

Typical values: 8-12 steps

```python
RTCConfig(execution_horizon=10)
```

**`max_guidance_weight`**: How strongly to enforce consistency with the previous chunk. This is a hyperparameter that can be tuned to balance the smoothness of the transitions and the reactivity of the policy. For 10 steps flow matching (SmolVLA, Pi0, Pi0.5), a value of 10.0 is an optimal value.

**`prefix_attention_schedule`**: How to weight consistency across the overlap region.

- `LINEAR`: Linear decay from inference_delay to execution_horizon
- `EXP`: Exponential decay (recommended for getting started)
- `ONES`: Full weight across entire execution_horizon
- `ZEROS`: Binary (full weight up to inference_delay, then zero)

**`inference_delay`**: How many timesteps of inference latency your system has. This is passed to `predict_action_chunk()` rather than the config, since it may vary at runtime.

## Remote deployment with an isolated trained runtime

The `policy_server_deployment` and `robot_client_deployment` entry points support
both modes. Select the same mode on both ends. The deployment pair uses protocol
version 4; update and restart both machines together. Action chunks are sent as
one dense tensor plus timestamps and step indices, avoiding repeated serialization
of the entire backing storage for every action row. Historical `*_rtc*` clients
do not support the deployment protocol and are rejected during setup.

For a Pi05 checkpoint trained with `rtc_training_max_delay=10` and
`chunk_size=50`, start the server with:

```bash
python -m lerobot.async_inference.server.policy_server_deployment \
    --host=0.0.0.0 --port=8080 --fps=30 \
    --rtc.mode=trained --trained.delay_steps=10
```

Keep the robot, camera, task, and address options from your existing
`robot_client_deployment` command and set:

```bash
--policy_type=pi05 \
--pretrained_name_or_path=/path/to/trained_rtc_checkpoint \
--rtc_mode=trained --fps=30 \
--actions_per_chunk=50 --trained.queue_threshold=25
```

These deployment options belong to the independent `rtc_trained.py` runtime:

- `trained.delay_steps` is a **fixed** commitment budget, defaulting to the
  checkpoint's `rtc_training_max_delay`. It must be positive and no greater
  than that training maximum. A larger budget preserves more old actions and
  tolerates more latency, at the cost of slower replanning.
- `trained.queue_threshold` is a **fixed** refill trigger, defaulting to half
  `actions_per_chunk`. It must cover `delay_steps` and be smaller than the chunk.
  The chunk must satisfy `2 * delay_steps <= actions_per_chunk <= model.chunk_size`.
- `trained.replan_on_result` defaults to `true`: after accepting a result, the
  deployment client allows a fresh capture on the next control tick, even if
  the queue is still above `queue_threshold`. This preserves single-flight
  inference and the fixed hard-prefix budget. Set it to `false` to use only
  the fixed queue trigger.
- Server and client `fps` must match and refer to policy endpoints. Optional
  action interpolation increases command frequency without changing this unit.
- Guided options such as `adaptive_rtt_trigger`, `rtt_trigger_margin_steps`,
  `rtc.execution_horizon`, and guidance weights do not alter the trained runtime.
  The trained path does not use guided cache references, per-action replacement
  arbitration, or the guided late-arrival tolerance.

Trained requests carry an explicit tensor of remaining absolute action endpoints,
including any endpoint currently being interpolated. The server converts it to
the checkpoint's model coordinates using the **current** observation state and
normalization, then calls native Pi05 hard-prefix sampling. For a prefix of
length `P`, the conditioned length is `min(trained.delay_steps, P)`. A successful
response replaces the mutable future queue without adding a splice bridge.
An empty tensor means the queue is actually empty; a missing prefix is an error,
never permission to run unconditionally.

When the server rejects a snapshot, it returns a `RemoteRTCRetry` response and
finishes that request. The client frees the matching in-flight slot and captures
new sensor data, execution progress, and remaining actions on the next control
tick. It never resubmits the old observation/prefix pair. This also applies to
guided cache misses and inference errors. If a returned chunk has become too
late in transit, the client rejects it and requests a fresh snapshot itself.
Trained mode requires actual consumed/frozen endpoints to fit inside the hard
prefix, with no additional guided tolerance; repeated rejections stop the client
after `trained.max_consecutive_rejections` attempts (default 5).

Both deployment and DAgger clients allow one pending request at a time, covering
observation capture, upload, and inference. Every admitted snapshot is sent;
there is no additional observation-similarity filter or cooldown. Once the
request completes, the next control tick can request another snapshot if the
queue needs refilling. Completed observations are not retained as filter
baselines, so their camera images can be released.

Both deployment and DAgger clients bound each pending request and runtime RPC
with `--request_timeout_s=30` (seconds, configurable). If a response is lost after
the server removes it from its mailbox, the next control tick after expiry frees
the request slot and captures a new observation and prefix. Late captures,
uploads, and results from abandoned requests cannot affect the replacement.
Set this timeout above normal camera, upload, and inference latency, including
the first inference. Transport timeouts do not update guided RTT estimates or
count as trained hard-prefix rejections.

Remove these obsolete options from existing deployment and DAgger commands or
configuration files; the entry points now reject them instead of accepting
settings that have no effect:

- Client: `observation_similarity_atol`, `cooldown_margin_steps`, and
  `aggregate_fn_name`.
- Server: `obs_queue_timeout`. Use `action_wait_timeout` for the server's action
  long-poll wait, or the client's `request_timeout_s` for the whole pending request.
  These timeouts serve different purposes.

The legacy `robot_client` and `policy_server` entry points retain their effective
`aggregate_fn_name` and `obs_queue_timeout` options, respectively.

A fatal exception escaping the local control loop marks the client as `fault`,
invalidates pending work, and signals process shutdown. The main thread then
closes the client even when the interactive prompt is waiting for input.
After cleanup, the entry point raises the worker failure so the process exits
with a nonzero status.
DAgger's handled command failures retain its existing pause/reset recovery.

Reset completion requires measured position feedback, not just successful command
delivery. After interpolation, the client keeps commanding the reset target until
every joint and gripper stays within tolerance for `--reset_settle_s=0.1` seconds.
The additional convergence timeout is `--reset_verify_timeout_s=5`. The default
tolerances are `--reset_joint_tolerance=0.02` and
`--reset_gripper_tolerance=0.001`, in the robot's action units (radians and meters
for Piper). Piper DAgger reads fresh physical CAN feedback from **both** arms.
Missing, non-finite, or out-of-tolerance feedback cannot admit the next rollout.
A failed reset leaves deployment in `reset_failed` and DAgger in `FAULT`; retry
`/reset` (Left Arrow in DAgger) successfully before starting again. If startup pose
capture failed, configure `reset_pose`; the client cannot claim a successful return
to an unknown pose.

DAgger ignores ordinary operator input during reset, saving, and other transitions.
Queued events are bound to the rollout generation and phase in which they were
pressed, so an early Right Arrow cannot start the next rollout after reset finishes.
Wait for the reset-complete prompt, restore the task environment, then press Right
Arrow again. Esc remains available during these transitions. A background recorder
failure also moves DAgger into `FAULT`, stops correction forwarding, and discards
the failed correction window; reset is required before another rollout.

Verbose RTC timing, overlap, and splice diagnostics are disabled by default.
Enable `--debug_rtc_diagnostics=true` on the client and/or server being inspected;
these records use the `DEBUG` log level. Warnings and errors remain enabled.
Client RTC diagnostics are emitted after releasing control and lifecycle locks,
so a slow diagnostic handler cannot retain those locks while printing a chunk.
With verbose diagnostics disabled, guided chunk merging also skips the diagnostic
tensor snapshots and before/after schedule scans. Queue-size history is collected
only with `--debug_visualize_queue_size=true`, avoiding per-tick history growth
during normal deployment and DAgger runs. When enabled, it retains the most recent
100,000 command-tick samples across pause and reset, then plots them on exit after
the robot has disconnected. Shutdown does not erase this diagnostic history.

Transport, reset fencing, and command interpolation remain shared deployment
infrastructure. The fixed delay and refill settings provide a baseline for
evaluating trained RTC independently of the guided runtime's scheduling changes;
they are deployment choices, not a claim of identical paper-level scheduling.

## How It Differs from the Async Inference in LeRobot

Both RTC and [async inference](./async) improve real-time robot control, but they solve different problems.

| Aspect        | Async Inference                                                            | RTC                                                 |
| ------------- | -------------------------------------------------------------------------- | --------------------------------------------------- |
| **Problem**   | Idle frames while waiting for inference                                    | Discontinuities between action chunks               |
| **Solution**  | Decouple prediction from execution                                         | Guide new chunks to continue smoothly from previous |
| **Benefit**   | No waiting, continuous action                                              | Smooth transitions, natural motion                  |
| **Best Used** | Async inference is best used with large models with high inference latency | Flow-matching based policies                        |

**Use both together** for maximum smoothness and reactivity!
