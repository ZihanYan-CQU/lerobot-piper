# 云端 π0.5 与本地 A2C2：迁移评估

日期：2026-10-15。状态：论文和源码审阅、设计建议；本次没有接入或运行修正头。

当前约束是云端 A100、客户端有 NVIDIA GPU、单个云端推理请求在途、chunk 长度 50，策略端点约 30 Hz，经插值以约 60 Hz 下发。目标是长预测、短开环执行，让新的观测尽快影响动作。客户端 GPU 型号、显存与端到端运行时间尚未确认。

建议并行推进图像传输减负与本地修正头研究。延迟估计只能帮助安排切换，无法让云端模型提前看到尚未到达的观测；本地闭环可以在云端等待期间响应新观测。修正头不能替代任意时长的云端重规划。

## 核验过的官方实现

用户提及的论文对应 [Leave No Observation Behind: Real-time Correction for VLA Action Chunks](https://arxiv.org/abs/2509.23224)，方法名为 Asynchronous Action Chunk Correction，缩写 A2C2。官方发布了 [LIBERO 代码](https://github.com/k1000dai/a2c2-libero)与 [Kinetix 代码](https://github.com/k1000dai/a2c2-kinetix)。本次重点阅读与机器人视觉输入更接近的 LIBERO 实现，固定版本为 `54dd088302a0ef3f50c4add3ec927ab94d76a406`。

| 官方代码 | 已核实的行为 | 对本项目的意义 |
| --- | --- | --- |
| [modeling_residual_transformer.py](https://github.com/k1000dai/a2c2-libero/blob/54dd088302a0ef3f50c4add3ec927ab94d76a406/src/lerobot/policies/residual_transformer/modeling_residual_transformer.py) | 当前图像和状态、基础动作、完整原始 chunk、时间特征、可选 VLM 特征进入修正网络。归一化动作空间内学习专家动作与基础动作的差，再相加并反归一化。 | 可迁移残差建模方式；需要适配本项目的 processor、动作单位和 π0.5 特征。 |
| [train_residual_transformer.py](https://github.com/k1000dai/a2c2-libero/blob/54dd088302a0ef3f50c4add3ec927ab94d76a406/src/lerobot/scripts/train_residual_transformer.py) | 在同一 episode 内选源时刻 s 和偏移 k，取 s 的预测第 k 项与 s+k 的观测、专家动作组成样本。 | 可利用已有 Piper 示教启动训练；修正头需要训练，基础模型可以冻结。 |
| [create_dataset_for_residualpolicy.py](https://github.com/k1000dai/a2c2-libero/blob/54dd088302a0ef3f50c4add3ec927ab94d76a406/eval_libero/create_dataset_for_residualpolicy.py) | 在示教数据上运行基础模型，缓存预测 chunk 和 VLM 表征。 | 可以离线生成缓存，不必在每次训练迭代运行 π0.5。 |
| [evaluation_libero.py](https://github.com/k1000dai/a2c2-libero/blob/54dd088302a0ef3f50c4add3ec927ab94d76a406/eval_libero/evaluation_libero.py) | 每个环境步读取新观测并修正当前基础动作；用 pending chunk 模拟给定延迟。 | 是研究参考实现，没有替本项目实现真实网络抖动、控制线程截止时间、重置与过期结果处理。 |

论文在仿真中验证方法。附录 A.5 报告 32M 修正头在 RTX 5080 Laptop 16 GB 上的 100 次平均推理时间约 4.7 ms；这不是当前客户端上的控制周期预算，也没有提供本项目所需的采集至下发 P99。参见[论文附录](https://arxiv.org/html/2509.23224v1#A5)。

## 建议的执行结构

云端继续用旧观测产生名义计划；本地用最新观测修正即将执行的一步：

```text
云端 π0.5 → 50 步名义 chunk + 少量上下文 → 本地修正头 → 30 Hz 策略端点 → 60 Hz 插值 → Piper
                                                    ↑
                              最新 RGB、关节状态、原 chunk 索引、观测年龄
```

建议原型的输入与输出为：

```text
corrected_target = base_target + correction(
    latest_images, latest_joint_state,
    base_target, immutable_source_chunk, source_chunk_index,
    source_context, source_observation_age, local_image_age
)
```

完整 chunk 和原始索引来自官方实现；显式加入两种观测年龄是本项目针对抖动和停顿的扩展建议。动作索引在停顿期间可能不增长，不能用 k/30 代替实际经过时间。原始 chunk 的索引也不能用全局动作步数对 50 取模获得。

在 30 Hz 策略周期内，修正计算的总预算约为 33.3 ms，必须包括图像预处理、数据拷贝和调度。先保留现有 60 Hz 插值，无需一开始就在每个电机 tick 运行视觉网络。每步新观测能够影响动作是目标，能否达标需要在实际客户端上测量。

云端重规划仍然尽早触发，不能为了修正头而增加固定执行长度。若云端一次请求需要 T 秒，单请求架构下新的云端计划产生速度仍受 T 限制；本地修正主要缩短局部反馈的等待时间，不能保证承担全新的语义任务或无限期纠正过期计划。

## 本项目需要修改的接口

| 位置 | 当前行为 | 迁移要求 |
| --- | --- | --- |
| `robot_client_deployment.py::_InterpolatedClient.control_loop_action` | 取出端点后交给插值器；已经进入插值的端点保持不变。外层持有生命周期和命令锁。 | 修正结果必须在端点提交前准备好。独立 worker 计算，控制线程只检查结果并原子提交，不在锁内等待相机或 GPU。 |
| 同文件 `_ScheduledAction` | 已有 source observation ID 与 raw action index。 | 使用这些标识；增加 generation、图像序号和截止时间校验，防止重置、换 chunk 后误用旧修正。 |
| 同文件 observation sender | 云端请求触发观测获取。 | 建立独立、持续更新的本地观测缓存，供云端请求和修正头共享。每个消费者只取最新快照，不建立待处理旧帧队列。 |
| `rtc_remote.py::RemoteRTCActionChunk` | 返回动作和 RTC 元数据，不携带 VLM 表征。 | 加可选的小型上下文字段，在客户端按 source ID 保存不可变完整 chunk；避免传输整个 KV cache。 |
| `modeling_pi05.py::sample_actions` | 现有 VLM 前缀 forward 返回值的第一项被忽略，保留 KV cache。 | 核验输出后，复用这一次 forward 的少量隐藏特征作为上下文；训练与部署使用相同提取方式，不额外运行一次完整 VLM。 |
| `piper_follower_PyAgxArm.py::send_action` | 下发前仍可能做关节和夹爪 EMA。 | 分别记录基础动作、修正目标、滤波后命令与测量状态。结合跟踪误差评估滤波造成的滞后，避免修正收益被额外平滑抵消。 |

动作空间建议先统一到后处理后的绝对关节/夹爪目标，并使用专门的归一化统计训练修正头。必须明确 π0.5 的相对动作重定位与修正发生的顺序。不能把旧观测下的相对动作直接与当前绝对角度相加。

为修正幅度、目标变化率和夹爪定义独立限制。修正结果超时或标识失效时，走现有有效动作或停顿策略；不要照抄 LIBERO 的全零动作兜底，因为 Piper 全零位置指令有实际运动含义。

ZMQ 相机还有两个需要处理的细节：`async_read()` 消费并清除共享新帧事件，不宜让两个独立消费者都等待它；`latest_timestamp` 当前是在接收解码后记录，并不是传感器曝光时刻。可复用非阻塞读取思路，但需要共享快照、帧序号和明确的时间戳语义。跨机器单程耗时不能直接用未同步的时钟相减。

## 与 RTC 前缀的关系

当前 guided 路径通过 `RTCActionRef` 从服务器缓存恢复名义动作，支持已有 splice bridge，不能表达任意学习到的残差。客户端如果改了实际提交的端点，服务器仍按旧引用恢复前缀，二者会失配。

trained 路径发送显式前缀，并在 `TrainedRTCClientRuntime.accept()` 检查返回前缀和请求快照相同。但请求发出后，本地根据新图像产生的修正并不在快照里。因此即使这项检查通过，也不能推出修正后的下发端点与该前缀一致。这是计划协议问题，不代表当前 RTC 本来就保证物理关节状态精确等于前缀。

回传已知修正和实际关节状态有帮助，但无法预先回传未来观测产生的修正。保留两种明确的设计选择：

1. 将 RTC 前缀定义为名义参考，本地修正作为反馈控制器。需要显式区分名义计划和实际提交目标，并在相同执行机制下训练、评估；不能沿用“硬前缀等于实际提交动作”的解释。
2. 在已承诺的前缀窗口内冻结修正。它更容易保持现有前缀契约，却会降低等待期间的响应性，与本次优化目标存在冲突。

因此建议先独立验证单请求异步 π0.5 + A2C2，并保留现有 RTC 作为比较基线。取得效果后再实验 guided RTC 的名义参考方案；严格 trained RTC 的组合另行设计。论文称方法与 RTC 互补，并不等于开源 LIBERO 示例已经验证了本项目的前缀契约。

## 无需训练就能推进的优化

1. **降低上传图像体积。** 本地日志 `logs/robot_client_deployment_1791887645.log:316` 等记录每次发送约 1.84 MB，接近两路 640×480 uint8 RGB 原图。若实际 checkpoint 与当前 π0.5 默认 224×224 输入一致，可以将等价 resize/pad 提前到客户端。两路原始像素从 1,843,200 字节变为 301,056 字节，约减少到 1/6.12。保持宽高比、颜色、数值范围与插值约定，调整传输元数据；“等价”需要用模型输入张量对照验证。
2. **再比较图像编码。** 基于端到端耗时和任务表现评估 JPEG 等方案；既有相机传输已压缩时避免无谓解码再编码。上传维持 uint8 或压缩字节，避免转 float32 后扩大四倍。传输耗时收益取决于实测带宽、编码成本和网络抖动，不能把像素减少比例当作整体加速比。
3. **消除观测积压。** 本地持续采集，发送时拿最新快照；预处理、图像传输与电机下发分离。控制 tick 不因获取相机新帧阻塞。
4. **单独优化服务器耗时和尾部抖动。** 根据实际加载配置和 profiler 分开看预处理、VLM 编码、去噪、RTC 引导、GPU 等待与后处理。再选择专用 GPU、预热、编译、精度或去噪步数实验，并验证策略质量。当前代码默认值不能证明服务端采用了同样配置。
5. **以新观测何时影响动作衡量收益。** 上轮增加的 `RTC RPC PHASES` 可区分服务器阶段与其余耗时；其中 `outside_server_ms` 包含传输、序列化、排队等，不能直接叫网络 RTT。还需要图像年龄和“观测被修正头使用→对应端点实际下发”的关联记录。

## 训练和验证顺序

第一阶段先完成传输和观测缓存优化，记录现有 guided/trained 的真实延迟分布、任务成功率、切换回退与停顿。

第二阶段冻结当前 π0.5，在 Piper 示教上缓存预测和上下文，训练修正头。按 episode 划分训练/验证集合。初始沿用官方的跨时刻监督，之后让样本覆盖日志里的实际 chunk 年龄与抖动。仅改变时间标签并不能合成停顿后的真实视觉和接触状态；这些情况需要回放环境或新增执行/人工纠正数据。若以后结合 RTC，缓存生成也要覆盖相应的前缀条件，不能仅在无前缀输出上训练后假定可直接泛化。

第三阶段在客户端进行只记录输出的运行，测量修正端到端 P50/P90/P99、错过截止时间比例、修正幅度，以及基础/修正/滤波后/实测关节之间的差异。小离线 MSE 不代表闭环成功，尤其不能用执行过的失败动作本身充当专家标签。

第四阶段做受控任务对比：当前 RTC、普通异步策略、普通异步策略加修正头。在一致的延迟条件、初始状态和任务下比较成功率、完成时间、回退、局部响应时间和停顿。合格后才研究 guided 混合方案；trained 混合方案需要单独验证前缀语义。

优先交付顺序：图像 payload 优化及共享观测缓存 → π0.5 缓存数据导出与修正头训练 → 本地独立 worker 和影子运行 → 受控执行 → RTC 组合实验。
